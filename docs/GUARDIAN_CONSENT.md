# 만 14세 미만 회원가입 — 법정대리인 동의 기능

## 사용자에게 보이는 흐름

**학부모가 자녀 가입을 승인하는 방식**입니다. 학생 연결 코드를 알고 있는 사람의 클릭만으로는 법정대리인 동의가 확인됐다고 처리하지 않습니다.

1. 학생이 가입 과정에서 생년월일로 만 14세 미만을 선택하면 회원 학습 기록 기능은 **비활성** 상태로 시작합니다. GUEST 체험은 계속 가능합니다.
2. 학생이 **15분 유효한 일회용 연결 코드**를 발급받아 학부모에게 알려줍니다.
3. 학부모는 별도 Google/Kakao 계정으로 가입하고 코드를 입력합니다. 이 단계는 계정 연결 요청이며 아직 승인 상태가 아닙니다.
4. 학부모 화면에서 **법정대리인 실명·관계·법정대리인 선언·아동 개인정보 수집/이용 동의**를 입력합니다.
5. 서버가 학부모의 **확인된 로그인 계정 이메일**로 아동 정보 수집 항목/목적/거부권/동의 회신 방법이 포함된 이메일을 전송합니다.
6. 학부모는 그 메일에 **법정대리인인 사실 + 동의 의사 + 요청번호**를 직접 명시하여 답장합니다.
7. 운영자는 수신 편지의 발신인/요청번호/명시적 동의 문구/법정대리인 선언을 확인하고 승인합니다.
8. 서버에서 승인하면 학습 기록 저장과 해당 학부모의 조회/숙제가 활성화됩니다. 동의 철회 시 기록에 대한 학생·학부모 접근은 즉시 중지합니다.

**법적 구별:** 화면의 체크박스는 동의 의사 표시이고, **동의 내용이 기재된 이메일 발송 및 법정대리인의 명시적 이메일 회신**이 동의 확인 절차입니다. 한국 개인정보 보호법 제22조의2와 시행령 제17조의2 제1항의 방식 가운데 이메일 회신 방법을 사용합니다.

- https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335069
- https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=289537

## 활성화에 필요한 운영 설정

코드에서는 설계/인터페이스/서버 권한/보안잠금을 구현했습니다. **실제 발송과 회신 확정을 위해서 운영사가 아래 설정을 해야 합니다. 이 설정을 하지 않으면 승인되지 않고 계정은 잠겨 있습니다.**

1. Supabase 새 프로젝트에 다음 SQL을 순서대로 적용:
   - `supabase/migrations/202611230001_membership.sql`
   - `supabase/migrations/202611230002_guardian_consent.sql`
2. 학부모 Google/Kakao OAuth의 이메일 제공 및 **계정 이메일 확인**을 구성합니다. 이메일 미제공 계정은 이 방법을 사용할 수 없습니다.
3. 동의 회신을 실제로 받을 수 있는 **운영사 전용 이메일 주소**를 준비합니다. 담당자가 수신함에 접근해 회신을 점검합니다. Gmail을 단순 광고 발송 주소로 이용하지 말고, 보유/삭제 정책을 마련하세요.
4. Resend 등 이메일 발송 서비스에 **회사 소유 도메인을 인증**하고 이메일 발송 API 키를 발급받습니다.
5. Supabase Edge Function `send-guardian-consent`를 **JWT verification 활성화** 상태로 배포합니다. 운영 환경에서 다음 비공개 Secrets를 설정합니다.

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_KEY
SUPABASE_SERVICE_ROLE_KEY=SERVER_ONLY_SECRET
RESEND_API_KEY=SERVER_ONLY_EMAIL_API_KEY
CONSENT_FROM_EMAIL=수학천재 <consent@YOUR_DOMAIN>
CONSENT_REPLY_TO_EMAIL=privacy@YOUR_DOMAIN
APP_ORIGIN=https://YOUR_ACTUAL_APP_DOMAIN
GUARDIAN_CONSENT_ENABLED=true
```

- `SUPABASE_SERVICE_ROLE_KEY`와 `RESEND_API_KEY`는 **Edge Function 비밀환경변수**에만 둡니다. Vite의 `VITE_*` 변수나 Git 저장소에 넣으면 안 됩니다.
- 메일이 스팸함에 들어가지 않도록 SPF/DKIM/DMARC 등 운영 도메인의 발송 인증을 설정하세요.
- 서버는 요청/이메일 주소를 로그인한 부모 계정 및 연결된 학생에 대해서만 찾고, 각 요청의 이메일은 한 번만 발송하도록 처리합니다. 동의 확인은 이 메일의 발송 성공만으로 승인하지 않습니다.
- 최종 약관·개인정보처리방침·보유기간·처리 위탁/국외이전, 문의처 및 동의 철회/삭제 프로세스를 법무/개인정보 책임자가 확정한 후 **동의 문서 버전**을 갱신해야 합니다. 현재 버전 `draft-2026-11-23`은 검수용 초안입니다.

## 운영자가 이메일 회신을 확인한 뒤 승인하는 방법

**고객의 체크박스만 보고 승인하면 안 됩니다.** 운영자는 수신함에서 실제 회신을 확인한 뒤 다음을 점검합니다.

- 발신 이메일이 요청에 등록된 **학부모 계정 이메일**과 동일한지
- 요청번호가 이메일에 기재된 일회용 요청 UUID와 일치하는지
- 법정대리인임을 명시하고 개인정보 수집·이용에 **동의한다는 문구가 명확한지**
- 반대·무응답·자동응답·의심스러운 대리인 요청이면 승인하지 않았는지
- 해당 이메일의 발송/수신 증빙을 접근 제한된 운영자 수신함에 남겼는지

수신 이메일의 RFC Message-ID 등 검증 증빙을 기준으로 SHA-256 참조값을 계산합니다(원문과 개인정보를 DB에 중복 보관하지 않음). 예:

```bash
printf '%s' 'trusted-inbound-email-message-id' | shasum -a 256
```

**Supabase SQL Editor (신뢰된 운영자 전용)**에서 실제 회신을 확인한 뒤에만 다음 함수를 실행합니다.

```sql
select public.verify_guardian_email_reply(
  'REAL_CONSENT_REQUEST_UUID'::uuid,
  'REPLACE_WITH_64_CHARACTER_SHA256_LOWER_HEX',
  'operator-reviewer-identifier'
);
```

`guardian_consent_requests.status`가 `sent`이고 연결된 학생인지 검사한 후에만 `verified`로 기록합니다. 이 함수는 일반 로그인 사용자의 RPC 권한이 **없습니다**. 브라우저에서는 승인 날짜, 이메일 증빙 해시를 변경할 수 없습니다.

동의 철회는 학부모 화면의 **법정대리인 동의 철회** 버튼에서 처리하고, 학생·학부모 학습정보 접근을 서버 RLS에서 차단합니다. 기존 수집 정보의 삭제/법령상 보존/보호자 신원확인 절차는 정식 출시 전 별도 운영 정책 및 기능을 마무리해야 합니다.

## 보안 및 법무 잔여 점검

- [ ] DB 마이그레이션을 실제 Supabase 프로젝트에 적용하고 **부모/학생 각각의 계정에서 RLS 권한 테스트**
- [ ] Resend 연동, 회사 발신 도메인 인증, 운영사 개인정보 회신 수신함 준비
- [ ] 테스트 메일 발송, 진짜 회신 확인 후 운영자 승인, 학생 대시보드 활성화까지 통합 검증
- [ ] 보관 기간, 동의 문구/처리방침, 제3자 위탁과 국외 이전, 연락처 법무 검수
- [ ] 법정대리인 신분에 관한 허위 신고·동일 기기의 계정 대리 사용 등 부정사용 대응
- [ ] 동의 철회, 연결 해제, 탈퇴 및 아동 정보 삭제 처리까지 검증
- [ ] **아동 정보가 OAuth 로그인 때 보호자 동의보다 먼저 수집될 수 있는 현행 인증 순서 개선:** 정식 출시 전 부모 주도 계정 생성 또는 신뢰된 성인 사전승인 및 이후 자녀 인증으로 재설계 필요
- [ ] 생년월일 자기 신고만으로 만 14세 여부를 정확히 검증할 수 없다는 한계를 고려한 연령 확인 정책 수립

위 마지막 두 항목 때문에 이 코드는 **검수용 PR**이며, 현재 상태를 '법률 준수 완료' 또는 '아동 회원가입 상용화 완료'로 설명하면 안 됩니다.
